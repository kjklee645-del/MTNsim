# GPU CPU Execution Paths

Date: 2026-03-11
Purpose: clarify which parts of MTNsim currently use GPU, which paths still fall back to CPU, and what should be migrated next.

## 1. Current Execution Split

| Area | Current path | GPU used now | Notes |
| --- | --- | --- | --- |
| Free-field distance attenuation | `update_noise_grid_gpu` | Yes | Used when no shielding/scene-aware propagation objects are active. |
| Basic receiver/grid accumulation | `update_noise_grid_gpu` | Yes | GPU path currently handles distance-based attenuation only. |
| Shielding with barriers/buildings | `update_noise_grid_gpu` hybrid or `update_noise_grid_cpu` | Partial | Distance attenuation and power accumulation can now run on GPU; context construction is still provider-driven. |
| Reflection correction | `update_noise_grid_gpu` hybrid or `update_noise_grid_cpu` | Partial | Reflection correction values are still built by the provider, then applied in the hybrid GPU path. |
| Diffraction correction | `update_noise_grid_gpu` hybrid or `update_noise_grid_cpu` | Partial | Same pattern as reflection. |
| Material-aware correction | `update_noise_grid_gpu` hybrid or `update_noise_grid_cpu` | Partial | Correction values can now be consumed by the GPU accumulation path. |
| Terrain-edge correction | `update_noise_grid_gpu` hybrid or `update_noise_grid_cpu` | Partial | Implemented through shielding-style terrain edge segments and can now flow through the hybrid GPU path. |
| Ground-surface correction | `update_noise_grid_gpu` hybrid or `update_noise_grid_cpu` | Partial | Broad-phase candidate scan can be tensorized; detailed correction still comes from the provider. |
| Vegetation-zone correction | `update_noise_grid_gpu` hybrid or `update_noise_grid_cpu` | Partial | Same pattern as ground surfaces. |

## 2. Current Switch Logic

Effective behavior in `RunService` today:

| Condition | Result |
| --- | --- |
| No shielding segments and `use_gpu=True` | GPU path can be used |
| Scene-aware propagation with `use_gpu=True` | Hybrid GPU path can be used |
| `use_gpu=False` | CPU path is used as the reference path |

In practice this means:
- `baseline`-style free-field runs can use GPU.
- `terrain_ground_vegetation` now also runs with `used_gpu = true` through the hybrid scene-aware path.
- CPU remains the reference path for correctness checks.

## 3. Why CPU Fallback Happens

Current blockers for full scene-aware GPU execution:
- shielding/reflection/diffraction contexts are still generated by the provider rather than fully tensorized kernels
- ground and vegetation corrections still use provider-side detailed evaluation after broad-phase candidate filtering
- material-aware corrections still depend on provider-built contexts rather than native tensor kernels

## 4. What Should Move To GPU Next

Recommended migration order:

| Priority | Computation | Why |
| --- | --- | --- |
| 1 | Shielding segment intersection and line-of-sight blocking | This is the main gate that disables GPU for barriers/buildings/terrain edges. |
| 2 | Reflection and diffraction context evaluation | These are downstream of shielding and must move with it to avoid mixed-path overhead. |
| 3 | Material-aware correction application | Once contexts are vectorized, material correction becomes a lightweight tensor step. |
| 4 | Ground-surface path checks | Needed to make terrain-aware scene effects feasible at larger scales. |
| 5 | Vegetation-zone path checks | Similar to ground surfaces, but can follow the same scene-mask strategy. |

## 5. Suggested GPU Strategy

A practical next strategy is:
1. precompute scene masks or compact scene arrays from `SceneModel`
2. vectorize `vehicle x POI x segment` blocking tests
3. compute reflection/diffraction gains from the same vectorized context
4. add tensor-based ground/vegetation correction masks
5. keep CPU as a correctness reference path during migration

## 6. Current Bottom Line

Current state:
- GPU is already used for simple free-field runs.
- GPU is now also used in a hybrid scene-aware path for terrain/barrier/building style runs.
- full tensorized scene-aware correction is still not complete.

So the next optimization goal is no longer to introduce scene-aware GPU usage, but to deepen it from hybrid accumulation into fully tensorized correction kernels.

## 7. Grid Snapshot Scheduling

The default project now stores a final grid snapshot without recomputing the full grid on every simulation step.

| Setting | Current behavior |
| --- | --- |
| `store_grid_timeseries = false` | receiver histories are updated every step, but the grid is computed only on the final step |
| `store_grid_timeseries = true` | full grid can still be computed each step when needed |

This change improves scene-aware CPU runs substantially without changing the final grid snapshot artifact.

## 8. Scene-aware CPU Batching

MTNsim now includes a `SceneAwarePropagationProvider` that can resolve `vehicle -> many POIs` corrections in one CPU path. This does not yet move scene-aware propagation onto GPU, but it reduces Python callback overhead and creates a cleaner migration target for later tensor/GPU work.

## 9. Scene Candidate Tensorization

MTNsim now has a tensor-ready candidate scan in the scene-aware propagation provider. It currently acts as an infrastructure step rather than a universal speed-up: for small POI sets the code falls back to the simpler Python path, while larger POI sets can use tensor-based broad-phase scene masking.

## 10. Scene-aware Hybrid GPU Path

MTNsim now supports a hybrid scene-aware GPU path. In this mode, the propagation provider still constructs correction values, but attenuation and power accumulation run through the GPU kernel.

Observed validation snapshot:
- reduced-size CPU vs GPU terrain/ground/vegetation run matched within about `2.6e-6 dB` on receiver means
- full-size `terrain_ground_vegetation` run now records `used_gpu = true`
